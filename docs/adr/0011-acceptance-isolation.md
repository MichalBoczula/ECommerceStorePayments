# ADR-0011: Isolated HTTP acceptance scenarios

Status: Accepted

Date: 2026-09-28

## Context

Unit tests and repository integration tests do not jointly confirm public HTTP status, error shape, Orders integration and durable Payment state. Acceptance scenarios must be reproducible and independent of test order.

## Decision

Use source `.feature` scenarios with pytest-bdd under `tests/acceptance`. Each scenario starts the real FastAPI lifespan with a new database name against the shared Testcontainers MongoDB replica set. The application probes MongoDB and creates indexes as in production; the fixture drops its database and closes clients in `finally`, including after assertion failures. Only the outbound Orders HTTP transport is controlled with `MockTransport`, permitting deterministic successes, invalid responses, timeouts and outages without replacing the Orders adapter. Terminal states for retry scenarios are prepared through the real MongoDB repository and domain transitions.

Record every scenario ID, operation, cause, expected status and public code in `docs/acceptance-matrix.tsv`. A test checks that every matrix ID has exactly one source scenario and a result assertion. The result step checks HTTP status, content type and safe problem representation against the matrix. Existing repository-level transaction/concurrency tests remain the detailed storage checks; acceptance covers the complete API flow including two concurrent first Pay requests.

Add an `acceptance` stage to the common CI script, local verification and PR workflow. Reports are generated by pytest when requested; separate JUnit/coverage artifacts and suite thresholds are PAY/15.

## Consequences

The suite requires Docker and a MongoDB replica set. It does not rely on a running Orders service or scenario execution order. Each scenario incurs FastAPI startup and database cleanup; the MongoDB container is shared only within the test session. A future external provider can be controlled at its HTTP boundary using the same approach.

## Alternatives considered

Reuse fake MongoDB collections: rejected because these tests must confirm actual persistence and startup indexes. Call a live Orders instance: rejected because unrelated service availability makes the suite nondeterministic. Seed terminal documents directly: rejected because that bypasses domain transitions and history transactions.
